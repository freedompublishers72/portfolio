# Upwork Economic Viability — Phase 1.1D Prompt Record

Exact prompt used for the Phase 1.1D Project Exploration task.

---

You are executing Upwork Economic Viability Phase 1.1D — Project Exploration.

OBJECTIVE

Move from technical-market/category analysis to the actual structure and behavior of Upwork projects.

The purpose is to understand how projects behave in practice, including what clients ask for, how scopes are written, how budgets relate to work, how long projects remain open, how competition develops, how projects are awarded, and what happens after the initial posting.

This phase is deliberately project-centric rather than category-centric.

INPUT

Use the strongest technical areas and project archetypes identified through Phases 1.1A–1.1C.

Also sample projects outside those areas where necessary to establish whether observed behavior is general or category-specific.

PROJECT LIFECYCLE

Where observable, investigate:

1. Job creation
2. Initial posting
3. Early proposal accumulation
4. Change in proposal count over time
5. Client activity
6. Interviews/messages if observable
7. Hiring
8. Time to hire
9. Project closure
10. Reposting or replacement
11. Subsequent related jobs from the same client

Do not assume that all lifecycle stages are observable through Upwork MCP. Record what can and cannot be measured.

PROJECT STATISTICS

Collect evidence for:

- fixed vs hourly
- budget
- duration
- proposal count
- Connect requirement
- client history
- client spend where available
- hire rate where available
- number of freelancers hired where available
- client location
- experience requirements
- qualification requirements
- screening questions
- interview requirements
- urgency
- project complexity
- technical stack
- number of technologies involved
- scope clarity
- scope ambiguity
- expected deliverable
- expected access
- communication requirements
- recurrence
- evidence of previous related projects

PROJECT BEHAVIOR

Investigate:

- How many projects appear genuinely small?
- How many are deceptively large despite small budgets?
- How often are budgets unrealistic?
- How often is the scope poorly specified?
- How often does the client appear to know the underlying technical problem?
- How often is the posted symptom different from the likely technical cause?
- How often does the client ask for diagnosis rather than implementation?
- How often does the job require access to production systems?
- How often does the job involve multiple systems?
- How often is urgency explicit?
- How often are projects abandoned or apparently dead?
- How often are projects hired quickly?
- How often do clients repeatedly purchase similar technical work?

SHORT-CONTRACT ANALYSIS

Specifically identify projects that plausibly fit:

- same day
- 1–2 days
- 3–5 days
- under 2 weeks
- under 1 month

For each duration class, measure:

- budget
- competition
- Connects
- technical type
- scope
- effective economics

Do not equate advertised duration with actual delivery time.

PROJECT QUALITY

Classify projects where possible as:

- clearly scoped
- moderately scoped
- ambiguous
- technically underspecified
- unrealistic
- likely scope-creep risk
- likely low-value
- potentially high-value diagnostic work

Use evidence rather than subjective impressions.

PROJECT ECONOMIC MODEL

Build project-level scenarios showing the relationship between:

budget → Connect cost → acquisition probability → delivery time → effective hourly return

Use multiple win-rate and delivery-time assumptions.

Also identify projects where acquisition economics are attractive only because the required delivery time is unrealistically low.

CLIENT / REPEAT DEMAND

Investigate whether projects produce evidence of:

- repeat clients
- recurring maintenance
- follow-up fixes
- related projects
- migration → repair
- repair → optimization
- security incident → remediation
- integration → maintenance
- infrastructure setup → support

The objective is to understand whether a single project can expose a larger demand chain.

OUTPUT

Produce:

1. Project lifecycle findings
2. Project statistics
3. Short-contract statistics
4. Scope/ambiguity analysis
5. Client behavior analysis
6. Competition behavior
7. Acquisition economics
8. Repeat/related-demand evidence
9. Project archetype statistics
10. Representative project records
11. Important anomalies
12. What cannot be observed
13. Implications for the final Phase 1.1 economic model

Do not turn project-level observations into unsupported generalizations.
