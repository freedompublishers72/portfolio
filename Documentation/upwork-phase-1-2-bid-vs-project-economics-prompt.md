# Upwork Economic Viability — Phase 1.2 Prompt Record

Exact prompt used for the Phase 1.2 Bid vs Standing Projects Economics task.

---

You are executing Upwork Economic Viability Phase 1.2 — Bid vs Standing Projects Economics.

OBJECTIVE

Determine how the Upwork marketplace economics differ for a technical supplier between its two fundamental acquisition hemispheres:

1. BIDDING GIGS
   Client creates a specific demand/project → supplier finds it → supplier submits a proposal → supplier wins or loses the work.

2. STANDING PROJECTS
   Supplier creates a defined, preconfigured technical service → the service remains available for clients to discover and purchase → supplier delivers the purchased Project.

Standing Projects are persistent commercial assets. They may be discovered through Upwork's own marketplace AND may be linked to from external resources such as:

- GitHub portfolio
- portfolio website
- technical case studies
- documentation
- search results
- referrals
- direct communications
- other external resources

Do NOT call Standing Projects "gigs" in this phase.

CORE QUESTION

For a technical supplier, which acquisition hemisphere produces better economics:

    Bidding Gigs
    versus
    Standing Projects

And:

    Can the two acquisition models complement one another?

The objective is NOT to assume one model is superior.

Determine the economics of each independently and then compare them using equivalent measures.

INPUT FROM PHASE 1.1

Use the completed Phase 1.1 evidence as the technical-demand foundation.

Phase 1.1 identified the technical universe, economically interesting project characteristics, project archetypes, budgets, competition, Connect economics, project durations, recurring demand, and the characteristics of technically constrained work.

Use those findings to determine which types of technical work could plausibly be sold through each acquisition hemisphere.

Do not redo Phase 1.1 unnecessarily.

PART A — BIDDING GIG ECONOMICS

Analyze the supplier economics of finding and bidding on existing client demand.

Measure where evidence permits:

- volume of relevant posted demand
- budget distribution
- project duration
- project type
- competition
- proposal/Connect requirements
- Connect cash cost
- proposal preparation time
- total acquisition time
- win rate requirements
- time to acquisition
- delivery time
- effective revenue
- effective profit
- effective hourly return
- client quality
- repeat-client potential
- follow-on work
- dead/stalled project rate
- scope risk
- scalability

Calculate economics across realistic scenarios rather than relying on one assumed win rate.

Separate:

- Connect cost
- proposal labour
- delivery labour
- waiting/time cost
- platform fees where measurable

Determine the actual acquisition cost of obtaining a project.

PART B — STANDING PROJECT ECONOMICS

Analyze the supplier economics of creating a defined Project that clients can purchase directly.

Do NOT assume that eliminating proposals automatically makes Projects economically superior.

Investigate the complete acquisition funnel:

    Project creation
        ↓
    marketplace/external visibility
        ↓
    client discovery
        ↓
    Project page/view
        ↓
    purchase/conversion
        ↓
    delivery
        ↓
    follow-on/custom work

Investigate where evidence permits:

- Project categories available
- demand for the underlying services
- Project pricing
- competing Projects
- marketplace visibility/discovery
- Project presentation requirements
- purchase/conversion evidence
- time required to create a Project
- time required to maintain/update it
- platform fees
- delivery time
- effective revenue
- effective profit
- effective hourly return
- repeat purchases
- custom follow-on work
- scalability
- persistence of the commercial asset

Explicitly investigate whether a Standing Project can function as a persistent acquisition endpoint rather than merely an Upwork marketplace listing.

EXTERNAL ACQUISITION

This is a required part of the Standing Project analysis.

Investigate the economics and mechanics of sending external traffic to a Standing Project.

Examples include:

    GitHub portfolio
        → relevant technical case study
        → Standing Project
        → purchase

    Portfolio website
        → technical service
        → Standing Project
        → purchase

    Search/referral
        → Standing Project
        → purchase

Determine what can actually be measured and what remains unknown.

Do not assume that external traffic converts.

PROJECT DESIGN

Investigate whether the technical work identified in Phase 1.1 can be converted into commercially useful Standing Projects.

Examples may include:

- diagnostic services
- repair services
- migration audits
- server diagnostics
- DNS/email diagnostics
- performance audits
- security remediation
- legacy-system assessment
- other technically bounded services

These are examples only.

Determine the actual Project archetypes from evidence.

For each promising Project archetype investigate:

- what is being purchased
- what is explicitly included
- what is excluded
- price
- expected delivery time
- diagnostic uncertainty
- scope-control mechanism
- likelihood of requiring custom work afterward
- suitability for external linking
- suitability for repeat purchase

Do not confuse a Standing Project with a generic service description. It must represent a defined purchasing transaction.

Compare Bidding Gigs and Standing Projects using equivalent economic measures.

At minimum compare:

|---|---|---|
| Demand source | | |

| Acquisition cost | | |
| Acquisition time | | |
| Competition | | |

| Price control | | |

Do not compare raw project prices alone.

The relevant comparison is:

    expected revenue
    − acquisition cost
    − acquisition labour
    − delivery cost
    − platform costs
    = expected economic return

Then compare the return against the supplier's time.

PART D — SAME SERVICE, TWO ACQUISITION MODELS

Where possible, take the same technical service and model it through both hemispheres.

For example:

    Existing client problem
        → Bidding Gig
        → proposal
        → win
        → delivery

versus:

    Defined diagnostic Project
        → client discovers Project
        → purchase
        → delivery

Compare the economics of the two routes.

This is important because the question is not merely:

"Which category of work is profitable?"

Phase 1.1 has already investigated that.

The question here is:

"Given the same underlying technical capability, which acquisition mechanism produces the better commercial result?"

PART E — CLIENT ACQUISITION BEHAVIOUR

Investigate the difference between:

    supplier chasing existing demand

and:

    client discovering a supplier-created offer

Study:

- friction
- trust requirements
- information requirements
- price sensitivity
- scope clarity
- buying intent
- decision time
- competition
- client qualification
- likelihood of repeat work

Do not invent conversion rates.

Identify measured values, external benchmark values, estimates, and unknowns separately.

PART F — COMPLEMENTARITY

Determine whether Bidding Gigs and Standing Projects can reinforce each other.

Investigate models such as:

    BID → Project → repeat purchase

    PROJECT → custom work

    PROJECT → larger custom project

    BID → portfolio evidence → stronger Project

    PROJECT → client relationship → custom technical work

    GitHub/portfolio → Project → client → custom work

    BID + PROJECT operating simultaneously

Determine which combinations are supported by evidence and which remain hypotheses.

PART G — ECONOMIC SCENARIOS

Construct realistic scenarios for:

1. Bidding-only
2. Standing-Projects-only
3. Mixed model

Use multiple assumptions for:

- acquisition rate
- conversion/win rate
- delivery time
- project value
- repeat work
- external traffic

Do not manufacture precision.

Show sensitivity to the variables that matter most.

Identify the break-even points where one acquisition model overtakes the other.

PART H — PLATFORM CONSTRAINTS

Document relevant Upwork constraints affecting either model, including where applicable:

- Connects
- fees
- Project rules
- proposal requirements
- eligibility/reputation requirements
- visibility/discovery
- external linking rules
- purchasing mechanics
- scope/payment constraints

Verify current platform rules rather than relying on historical assumptions.

Produce a complete Phase 1.2 report containing:

1. Executive summary

4. Standing Project economics
5. Standing Project external-acquisition economics
6. Same-service Bid vs Project comparison
7. Project archetypes suited to each model
8. Client acquisition comparison
9. Repeat/follow-on economics
10. Complementarity analysis
11. Bidding-only scenario
12. Standing-Projects-only scenario
13. Combined scenario
14. Break-even/sensitivity analysis
15. Platform constraints
16. Evidence-quality assessment
17. Unknowns requiring further measurement
18. Implications for Phase 1.3

EVIDENCE RULES

Clearly distinguish:

A — directly measured
B — directionally supported
C — hypothesis requiring testing
D — unknown/unobservable

Do not treat absence of observable Project sales data as evidence that Projects do not sell.

Do not treat the existence of a Project listing as evidence that it generates sales.

Do not assume marketplace visibility.

Do not assume external traffic converts.

Do not assume bidding wins.

Do not assume that eliminating Connects eliminates acquisition cost.

The purpose of Phase 1.2 is to determine the economic characteristics of the two acquisition hemispheres and establish whether one, the other, or a combination warrants further investigation.

Do not produce a generic conclusion such as "freelancing is viable."

The final conclusion must specifically answer:

    How does Bidding Gigs compare economically with Standing Projects?

    Which project types fit each acquisition mechanism?

    What does each mechanism actually cost the supplier?

    Where does each mechanism make or lose money?

    Can Standing Projects become persistent, externally linkable acquisition assets?

    Can Bidding Gigs and Standing Projects complement one another?

    What evidence is still required before choosing an operating model?
