Event-Driven Full-Page Caching

A custom page-caching system for a production WordPress platform that serves pre-generated HTML early in the WordPress lifecycle — skipping template rendering and exiting before normal page generation — with event-driven invalidation, self-verifying regeneration, and tested failure recovery.

Part of a larger private production system. Project names, domains, and operational details are anonymized; the engineering described is real and verifiable within that system.

Context

The platform is a production WordPress site behind a CDN where most traffic is anonymous and content changes are editorial rather than continuous. For that traffic profile, repeatedly rendering unchanged pages is wasted work — but a cache that silently serves stale content, or breaks when generation fails, is worse than no cache.

What was needed was a cache whose lifecycle was predictable: content changes invalidate the right routes, regeneration proves it actually happened, failures are detected rather than masked, and the whole thing can be reasoned about from its metadata.

Problem

The engineering problems a production page cache must solve:

  • Capturing complete HTML responses without corrupt files ever reaching visitors.
  • Keeping cache synchronized with content — posts, menus, settings, and terms all change what pages should contain.
  • Avoiding stale and orphaned entries — including the subtle case where a post's slug changes and the old route's cache becomes unreachable but still on disk.
  • Handling concurrent generation — two requests for the same missing page must not produce racing writes.
  • Detecting failed or incomplete generation — a regeneration that returns an HTTP 200 through a CDN is not proof that fresh HTML was captured.
  • Recovering from inconsistency — "ghost" entries, stale locks, and divergent metadata all need tested recovery paths.

Constraints

  • Lifecycle position. The cache engine runs inside WordPress: it hooks template_redirect, by which point core, plugins, theme, and the main query have already executed. What it skips is template rendering and the rest of page generation — not the bootstrap. That distinction drove every design decision below, and it is the honest way to describe the mechanism.
  • Only safe requests may be cached — GET/HEAD, no logged-in users, no admin/REST/AJAX/feeds/search/previews, and only canonical query strings.
  • A stale response may only be served inside a bounded window — a failed regeneration must never leave a route serving stale content forever.
  • Cache freshness is primarily event-driven (content changes trigger invalidation); the TTL exists as a safety fallback, not the primary mechanism.
  • Regeneration runs behind a CDN, so success cannot be trusted to a response header alone — it must be cross-checked against the cache's own metadata.

What was built

A full-page HTML cache organized as a per-route lifecycle. On each eligible request the engine computes a canonical route and consults a metadata registry: a valid entry is served immediately with a HIT status and the request exits; an invalidated entry inside its grace window is served STALE while a background regeneration is scheduled; a missing entry triggers capture.

Capture is deliberately defensive. A per-route lock allows one generation at a time and expires on its own if a worker dies. New HTML is written to a temporary file, validated (including a minimum-size check that rejects error pages and truncated output), and only then atomically renamed into the live path — a visitor can never read a half-written file. Invalidation is event-driven: content lifecycle hooks (publish, update, delete, trash/restore, slug changes, menu edits, customizer saves, term edits) invalidate the affected route, the homepage when listings change, or the whole site when global elements change — and schedule a warm so the next visitor gets a fresh page rather than a cold rebuild.

Regeneration is verified, not assumed. A regeneration response carries a cache-status marker plus a generation timestamp, and the engine cross-checks both against the stored metadata — because a CDN can legitimately return a marked response whose body was never captured. A scheduled health check watches for failures and alerts, and the recovery paths for stale locks and inconsistent "ghost" metadata are tested behaviors, not hopes.

Outcome

  • A complete custom caching subsystem of roughly 4,000 lines — a ~2,600-line engine, a ~1,200-line administration interface, and lifecycle wiring — plus a dedicated test suite.
  • Eight dedicated test files covering the properties that matter for a cache: invalidation coverage, metadata concurrency, state-agreement invariants, ghost-entry reconciliation, end-to-end ghost recovery, and alert/remediation behavior.
  • The project record contains a formal certification and freeze of this module. That is cited as historical project evidence: it documents what was verified at that point, not the current runtime state — indeed the recorded certification values and the current constants have since drifted apart, which is exactly why the distinction matters.

Technical evidence

Architecture
  • Eligibility layer — decides whether a request is cacheable at all (method, auth state, request class, canonical query string).
  • Route model — the cache is addressed by canonical route, not by URL accidentals.
  • Lifecycle position — delivery hooks template_redirect; WordPress has fully bootstrapped when the engine runs. It skips rendering, not bootstrap.
  • Store — generated HTML files plus a metadata registry recording generation time, duration, and invalidation state per route.
  • Concurrency — per-route capture locks with automatic stale-lock expiry.
  • Staleness policy — bounded stale-while-revalidate window; past the window a route regenerates rather than serving stale forever.
  • Edge cooperation — short browser/CDN cache lifetimes with stale-while-revalidate semantics, and an origin-bypass path for internal generation requests. Some requests are served by the CDN edge without reaching the origin — that is ordinary HTTP caching, separate from this engine.
Implementation
  • Atomic capture — write to a temporary file, validate (including a minimum-length check that rejects error responses), then rename into place.
  • Capture locks — one generation per route; locks older than a fixed timeout are treated as dead and removed, so a crashed worker cannot wedge a route.
  • Event-driven invalidation — content hooks invalidate the affected route and the listing homepage; slug changes hard-clear the old route to prevent orphaned files; global changes (menus, customizer, front-page setting) invalidate all.
  • Verified regeneration — success requires the regeneration status marker and a generation timestamp and a metadata freshness check; the header alone is explicitly not trusted.
  • Health monitoring — a scheduled check plus alerting on generation failure.
  • Bounded storage — the cache log rotates within a capped line count on a deferred-rewrite threshold.
Verification

Evidence held in the private project record:

  • Dedicated cache test suite — eight test files.
  • Invalidation-coverage tests, a state-agreement invariant test, and metadata-concurrency tests.
  • Ghost-entry reconciliation and end-to-end ghost-recovery tests.
  • Alert/remediation regression tests.
  • A formal certification and freeze record for the module.

The certification is historical project documentation — it proves the system passed a formal gate when certified, and is not presented as live runtime verification. (The certification record and the current code already differ on at least one constant, which the project record itself documents.)

Limits
  • The cache does not bypass the WordPress bootstrap. Serving happens at template_redirect, after core, plugins, theme, and the main query have run. The savings are in skipped template rendering and page generation, not in skipping WordPress.
  • It is not a web-server static-file cache — no advanced-cache.php drop-in or nginx cache-serving configuration is part of this implementation.
  • Edge-cache hits (CDN/browser) can bypass the origin entirely, but that is generic HTTP caching — not a property this engine claims.
  • The production codebase is private; this page describes the system rather than publishing it.
  • No performance percentages, throughput figures, or traffic outcomes are claimed — the evidence supports the engineering, not invented metrics.
