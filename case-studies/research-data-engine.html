Framework-Independent Research & Data Engine

A Python research and data engine that acquires, normalizes, stores, and evaluates external data through source-specific adapters — kept deliberately independent of WordPress behind a small REST boundary, with scheduled unattended collection and empirical scoring of its own probabilistic forecasts.

Part of a larger private production system. Project names, domains, provider identities, and operational details are anonymized; the engineering described is real and verifiable within that system.

Context

The system is a private research platform: a WordPress site presents research outputs to its operator, but the analytical core had to be able to outlive any single CMS, run unattended, and be testable without a web framework underneath it.

The engine continuously acquires data from multiple external sources, keeps a durable and auditable record of what was collected, runs a staged analysis pipeline over that data, and — critically — measures the accuracy of the probabilistic forecasts it produces rather than assuming they are good.

Problem

The engineering problems a system like this must solve:

  • Acquiring heterogeneous external data — multiple sources with different APIs, authentication schemes, cadences, and payload shapes, without letting any source's quirks leak into the core.
  • Normalizing incompatible representations — every source describes similar underlying concepts differently; analysis needs one canonical model.
  • Persisting data so analysis is auditable — what was collected, when, from which source, and whether it arrived intact all have to be reconstructable later.
  • Evaluating forecasts empirically — probabilistic outputs are only meaningful if the system can score its own past predictions against resolved outcomes.
  • Keeping the engine framework-independent — the runtime must not depend on WordPress, even though a WordPress site is how results are presented.
  • Running unattended — collection happens on schedules around the clock, so locking, rate limiting, and failure isolation are requirements, not niceties.

Constraints

  • Framework independence is a hard boundary. The engine must run from the command line and over REST with zero WordPress dependencies — and that property is enforced by a dedicated test, not by convention.
  • WordPress is a client, not a dependency. All PHP-to-Python traffic crosses a single token-authenticated REST boundary; the WordPress plugin contains presentation and control logic only.
  • Per-source isolation. Each data source is an adapter pair — a collector and a storage module — written against a shared contract, so a source change cannot ripple into the core.
  • Scheduling is orchestration, not engine internals. Collection is driven by external schedulers against a per-source cadence registry; collectors are lock-guarded so overlapping runs cannot corrupt a store.
  • Automation stops at drafts. The pipeline produces private draft research outputs for human review; the engine never publishes or acts on its own conclusions.

What was built

A framework-independent Python engine — roughly 59,000 lines across about 200 modules — exposed through a CLI and a small token-authenticated HTTP server. That server is the sole boundary between the WordPress world and the engine: it runs the staged research pipeline as background jobs and reports status back.

Acquisition is adapter-based. Nine source-specific adapter packages each provide a collector and a storage module (plus backfill where a source supports history), all written against a shared adapter contract. A collection framework supplies what every collector needs but none should reinvent: per-source collection specifications, run locks, rate limiting, and pagination. A separate provider framework — contracts, a registry, a capability model, and a normalization boundary — integrates two external market-data providers behind the same discipline.

Persistence is layered. Per-source storage modules write canonical records; a recorded-ingestion catalog tracks what was collected, when, and with what integrity checks; schemas are managed through SQL migrations rather than ad-hoc changes. Analysis sits behind formal boundaries: a valuation engine built on immutable domain objects, a recommendation engine behind its own public boundary, and a calibration layer with metrics and significance testing.

The engine scores itself. A forecast-scoring pipeline records every probabilistic output in a ledger, resolves forecasts against observed outcomes, and computes Brier scores — with counterfactual evaluation alongside — so accuracy is measured, not claimed.

Around the core, cron dispatchers, a per-source cadence registry, lifecycle cleanup, and a health watchdog run collection unattended. On the WordPress side, a thin client (~10,500 lines) talks to the engine only over REST — administrative views, health pages, and a set of REST endpoints — and pipeline output arrives as private draft posts awaiting human review.

Outcome

  • A framework-independent Python engine of roughly 59,000 lines across about 200 modules, plus a ~10,500-line WordPress thin client that contains presentation and control logic only.
  • Nine source adapters behind a shared contract, a provider framework with two external provider implementations, and a collection framework supplying specs, locks, rate limiting, and pagination.
  • An empirical self-evaluation loop: forecast ledger, outcome resolution, versioned Brier scoring, and counterfactual evaluation — the system's accuracy is a measured quantity inside it.
  • More than 130 Python test files plus a TypeScript spec suite for the WordPress client, including a dedicated test that enforces the engine's independence from WordPress.
  • The project record contains formal certification and freeze documents for the engine's major subsystems. These are cited as historical project evidence: they document what passed verification gates at the time, not the current runtime state.

Technical evidence

Architecture
  • Framework-independent core — the engine has no WordPress imports; it is operable from the CLI and over a token-authenticated HTTP interface that runs pipeline stages as background jobs.
  • Staged research pipeline — a canonical runtime executes ordered stages (discovery, qualification, evidence collection, analysis, recommendation, draft output) as discrete, inspectable units.
  • Adapter contract — each source supplies a collector/storage pair against a shared contract; indexers sit above the stores rather than inside collectors.
  • Collection framework — per-source collection specifications record each dataset's approved cadence and invocation mechanism; run locks and rate limiting are shared infrastructure.
  • Provider framework — contracts, a registry, a capability model, and a normalization boundary, with two provider implementations carrying their own authentication and normalization.
  • Analysis boundaries — valuation and recommendation each sit behind a formal public boundary object over immutable domain types; calibration contributes metrics and significance testing.
  • WordPress thin client — an engine client that speaks REST only, administration pages, REST endpoints, and a health-check framework; no engine logic lives in PHP.
Implementation

Selected engineering decisions:

  • One REST boundary — a single token-authenticated server is the only path between WordPress and the engine, so the framework boundary has exactly one door to audit.
  • Cadence as data — collection schedules live in a per-source registry with explicit due-checks; a frequent wake-up tick asks each dataset whether it is due rather than hard-coding intervals per job.
  • Lock-guarded collectors — overlapping runs of the same collector are prevented by design, so a slow source cannot corrupt its own store.
  • Recorded ingestion — acquisition is cataloged with integrity tracking, making later analysis auditable against what was actually collected.
  • Immutable domain objects — valuation inputs and results are modeled as immutable types, keeping analysis stages free of hidden mutation.
  • Versioned scoring — forecast scoring is implemented as a named, versioned method over a persistent forecast ledger, so scores are reproducible and the scoring rule itself is explicit.
  • Drafts, not decisions — the pipeline's last automated step produces a private draft for human review; editorial and action decisions stay outside the system.
Verification

Evidence held in the private project record:

  • More than 130 dedicated Python test files across the engine, collection framework, providers, and workflow — including a test that verifies the engine carries no WordPress dependencies.
  • A TypeScript spec suite covering the WordPress client.
  • Formal certification and freeze records for major subsystems, produced under a documented lifecycle (designed → authorized → implemented → verified → certified → frozen).
  • An extensive certification archive: verification reports, remediation records, and independent audit documents.

These are historical project documents: they establish that the work passed formal verification gates when certified, and are not presented as a claim that every component or historical test is currently passing. Suite sizes are file counts from the project record — evidence of coverage breadth, not a runtime guarantee.

Limits
  • The production codebase is private; this page describes the architecture rather than publishing it.
  • No accuracy percentages, performance benchmarks, or business outcomes are claimed — internal scoring exists, but this page does not publish its figures.
  • Certification evidence is historical — it should not be read as current runtime verification.
  • The collection cadences and source set are configured for one deployment; this is not a general-purpose product.
  • The WordPress component is a thin client for this engine — not a portable plugin for arbitrary WordPress sites.
