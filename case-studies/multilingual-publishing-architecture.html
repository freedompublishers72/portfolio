Multilingual Publishing Architecture

A custom WordPress architecture that routes, manages, and serves content in multiple languages — including languages written in non-Latin scripts — as first-class content rather than as translated copies of pages.

Part of a larger private production system. Project names, domains, and operational details are anonymized; the engineering described is real and verifiable within that system.

Context

The system is a production multilingual publishing platform: a content-heavy WordPress site that publishes in English plus additional languages, including languages written in non-Latin scripts.

Multilingual publishing here meant more than translating page text. URLs had to identify a language, every request had to resolve to the correct translated post, listings and feeds had to stay inside one language at a time, and editors needed a managed translation workflow — not a folder of hand-edited duplicates.

Problem

WordPress does not natively provide the properties this system needed:

  • Language-prefixed routing. Requests such as /<lang>/some-page/ had to be recognized as a specific language's version of a page, while plain URLs continued to serve the default language untouched.
  • Translation resolution. Given a language and a path, the system had to find the correct translated post — including when the translation existed but was not yet publicly published.
  • Native-language URL slugs. Translated content needed URLs in its own script, not transliterated English — which meant making percent-encoded Unicode slugs work correctly inside WordPress's permalink machinery.
  • Content and query separation. Archives, feeds, and listing queries had to be constrained to the request's language so that content could not leak across language boundaries.

Constraints

  • Translations can legitimately exist as drafts pending review, so resolution could not depend on the post's published status alone — but draft access had to be controlled, not a public back door.
  • Language detection could not silently redirect users: an explicit language prefix in the URL always wins, and browser Accept-Language is consulted only when the URL carries no language signal — and only toward translations that actually exist.
  • Language routing had to leave the rest of WordPress alone: administration screens, the REST API, login, cron, feeds' internals, and static assets are excluded.
  • Only approved, deployed languages may be routed — an arbitrary two-letter prefix is not a language.

What was built

A dedicated multilingual subsystem inside WordPress, built around a request pipeline rather than a page plugin:

A language router intercepts each request early in the WordPress lifecycle, detects the language signal — an explicit URL prefix first, browser language only as a fallback — and establishes the request's language context. A slug handler and translation resolver then map the language plus the remaining path onto the correct translated post, resolving native-language slugs and, under controlled rules, translations that are still in draft review. A query enforcer keeps subsequent listing queries inside that language so archives and listings cannot leak foreign-language content.

Behind the request path sits the editorial machinery: a translation manager with its own database layer (translation jobs, field-level translated content, an operation log, and translation memory with field-level hashing so changed source text is detectable), integration with a cloud machine-translation provider's API, WP-CLI commands and batch processing for bulk translation work, a locale switcher for visitors, and a custom administration interface for managing the whole pipeline.

Outcome

  • A complete custom multilingual architecture of roughly 15,700 lines across about 30 component classes — routing, resolution, slug handling, query enforcement, translation management, provider integration, batch tooling, and administration.
  • Accompanied by a dedicated test suite of more than 25 test files covering routing, slug boundaries, lifecycle behavior, feed isolation, and cache-language interaction.
  • The project's own documentation records a formal certification and freeze of this architecture (including regeneration and verification of 24 published translations across two additional languages). That certification is cited here as historical project evidence — it documents what was verified at that point in the project, and is not a claim about current runtime state.

Technical evidence

Architecture

Responsibilities are separated so each boundary is testable:

  • Language router — entry point; prefix detection, rewrite rules, language query var, fallback policy.
  • Language context — single source of truth for the request's language, consumed by every other component.
  • Query enforcer — constrains listing/archive queries to the resolved language.
  • Slug handler — generates, stores, and resolves native-language (percent-encoded Unicode) slugs.
  • Translation manager — the editorial workflow: job lifecycle, field-level content, staleness, review states.
  • Provider integration — adapter to a cloud machine-translation API behind an internal contract.
  • Translation database layer — four purpose-built tables: jobs, fields, operation log, translation memory.
  • Locale switcher — front-end language navigation between available translations.
  • WP-CLI operations — batch translation, remediation, and maintenance commands plus a scheduled bridge.
Implementation

Selected engineering decisions:

  • Prefix routing over query strings — a language-prefixed path is canonical, cacheable, and unambiguous; English URLs are never rewritten.
  • Explicit prefix beats browser language — Accept-Language is consulted only when the URL carries no prefix, and only redirects toward translations that exist, avoiding open redirects.
  • Native Unicode slugs — translated posts keep their own-script slugs, stored in WordPress's encoded form and resolved back at request time.
  • Resolution before rendering — language detection runs early in the request lifecycle, before template handling and before the page cache.
  • Controlled draft resolution — translations in review are resolvable through query-layer injection that does not alter the post's stored status.
  • Field-level infrastructure — translated content is tracked per field with hashing, so edits to source text mark exactly which translations went stale rather than invalidating whole posts.
  • Batch operations via WP-CLI — bulk translation runs as scripted commands with a scheduled bridge, not ad-hoc admin clicks.
Verification

Evidence held in the private project record includes:

  • More than 25 dedicated multilingual test files — covering routing, slug-boundary behavior, lifecycle and staleness, feed isolation, cache-language interaction, hook ordering, and certification integrity.
  • Formal certification and freeze artifacts for the architecture, produced under the project's documented verification workflow.
  • A recorded regeneration exercise in which 24 stale translations were re-run through the pipeline and verified (field hashes, relationships, publication state).

These are historical project documents: they establish that the work passed formal verification gates at the time, and are not presented as live runtime certification of the system today.

Limits
  • This is a purpose-built architecture for one production platform — not a plug-and-play multilingual product, and no claim is made that it drops into an arbitrary WordPress installation unchanged.
  • The production codebase is private; this page describes the architecture rather than publishing it.
  • Certification evidence cited above is historical — it should not be read as current runtime verification.
  • No traffic, ranking, revenue, or accuracy outcomes are claimed; the evidence supports the engineering itself, not downstream business metrics.
